# Fine tune target

GPT-OSS-20B was released by OpenAI as a post-trained, open-weights model, but
it’s not RLHF-aligned to the level of GPT-4 or ChatGPT.

It’s "post-trained" mostly via instruction tuning + synthetic preference data,
not full-scale human RLHF.

> Target
> make it more GPT-4-like

You can specialize it with a small, targeted fine-tune to teach conversational
reasoning norms:

- SFT
  Curate a few thousand examples of instruction → chatty, reasoning-oriented
  answers (can be synthetic using GPT-4). Make it follow prompts more
  conversationally.

- DPO
  Pair neutral vs. “GPT-4-style” answers and mark the latter as preferred. Nudge
  tone, reasoning style, and helpfulness.

- Eval
  Use win-rate or “helpfulness” scoring (GPT-4 as judge). Quantify alignment gain.

# datasets selection

How do I choose and structure my datasets so my local GPT-OSS-20B becomes more
GPT-4-like in reasoning and tone ?

- Instruction-Response (SFT data)
  Alpaca, ShareGPT, Databricks-Dolly, OpenOrca, SlimOrca, or your custom prompt
  logs Teaches the model to follow instructions and speak naturally.

- Preference Pairs (DPO data)
  Synthetic comparisons generated by GPT-4: for each prompt, produce two
  candidate answers (one dull or technical, one friendly/reasoning-style) Teaches
  style and helpfulness differences.

- RAG Evaluation Set
  30–50 real retrieval + answer pairs from your local LangChain experiments
  Measures improvement in reasoning and tone in your actual use case.

## 🧩 Dataset & Tokenization

### 1. Subset Dataset for Smoke Test

Use:

```python
small_dataset = full_dataset.select(range(5))
# or
small_dataset = full_dataset.shuffle(seed=42).select(range(n))
```

### 2. Print After `apply_chat_template`

Safe to print once per batch — doesn’t affect batching or mapping.

### 3. Role of `return_tensors`

Defines tokenizer output type:

- `"pt"` → PyTorch tensors
- `"np"` → NumPy arrays
- `None` → Python lists (best for Trainer)

### 4. Trainer Dataset Input

Trainer expects **tokenized tensors** (`input_ids`, `attention_mask`), not raw text.

### 5. Tokenization Best Practice

Let tokenizer handle padding and truncation automatically; avoid manual `[ids[0]]` or flattening.

### 6. Max Length Configuration

Defined during tokenization (`max_length` or `max_seq_length`), **not** inside Trainer.

### 7. Why DPO Has `max_length`

Controls prompt + completion size for reward loss comparison.

### 8. Recommended `tokenize_fn`

Clean version:

```python
def tokenize_fn(examples):
    return tokenizer(
        examples["text"],
        truncation=True,
        padding="max_length",
        max_length=MAX_SEQ_LEN,
    )
```

### 9. Returning Tokenized Data

Both work:

```python
return {"input_ids": tokenized["input_ids"], "attention_mask": tokenized["attention_mask"]}
# or
return tokenized  # preferred and cleaner
```

### 10. ValueError “too many values to unpack”

Occurs if model receives malformed batch (e.g., tensor shape mismatch).

---

## ⚙️ Trainer & Config

### 11. TRL `SFTTrainer` Finds `"text"` Automatically

Default field: `dataset_text_field="text"` inside `SFTConfig`.

### 12. `unsloth.trainer.SFTTrainer` vs. TRL’s

- **Unsloth:** Faster, optimized for limited VRAM (LoRA, Flash Attention).
- **TRL:** Standard, more flexible for research.

### 13. Unsloth’s `"text"` Detection

Yes — automatically detects the `"text"` field.

### 14. Config Differences

Unsloth has internal optimized defaults; TRL uses full `TrainingArguments`.

### 15. Which Is Better?

- **TRL:** For Research Reproducibility.
- **Unsloth:** For fast, efficient fine-tuning on small GPUs (e.g., T4).

---

## 📏 SFTConfig & Sequence Length

### 16. `SFTConfig` and `max_seq_length`

Present in recent TRL versions. Defaults to model’s `max_position_embeddings` if unspecified.

### **17. `max_seq_length` vs. `max_length`**

- `max_seq_length`: Truncation limit during **training**.
- `max_length`: Max tokens during **generation/evaluation**.

### 18. Config vs. Model-Level Max Length

- `FastLanguageModel.from_pretrained(max_seq_length)` → defines model architecture limit.
- `SFTConfig.max_seq_length` → defines data input truncation at training time.

## ⚡ Training Performance Notes

### 19. T4 Out-of-Memory Fixes

- Reduce `max_seq_length` (e.g., 512–1024).
- Use `gradient_checkpointing=True`.
- Lower batch size or switch to Unsloth.

### Understand the model format

🔹 unsloth/gpt-oss-20b(Designed for inference, not backprop)
✔️ MXFP4 Expert weights are stored in MXFP4
✔️ MoE-native quantization
✔️ Fast inference
❌ Standard nn.Linear
❌ Cannot be trained with QLoRA directly

LoRA requires: W_out = W + A @ B, But MXFP4 experts are packed, fused, and
kernel-optimized. There is no exposed W tensor to modify.

🔹 unsloth/gpt-oss-20b-unsloth-bnb-4bit
✔️ Converted to standard Linear layers
✔️ Quantized with bitsandbytes 4-bit
✔️ QLoRA-trainable
❌ Slower inference

| Format           | Use case                            | Can `llama.cpp` use it? | Notes                      |
| ---------------- | ----------------------------------- | ----------------------- | -------------------------- |
| MXFP4            | Inference / training inside Unsloth | ❌ No                   | Fast 4-bit format          |
| Merged FP16/BF16 | Export to HF, vLLM, llama.cpp       | ✅ Yes                  | Needed before quantization |
| Q4_K_M GGUF      | Efficient GPU inference (llama.cpp) | ✅ Yes                  | Quantized from merged FP16 |

### training format

When using `unsloth/gpt-oss-20b` as base model, Unsloth does a conversion step internally.

**GPT-OSS disk format ≠ training format**

```
MXFP4 MoE experts
   ↓
Unpack MXFP4 → FP16 dense Linear weights
   ↓
Replace MoE kernels with standard nn.Linear
   ↓
Quantize FP16 → BNB NF4
   ↓
Attach LoRA adapters
```

**Precision in training**

| Component      | Precision           |
| -------------- | ------------------- |
| Base weights   | **BNB 4-bit (NF4)** |
| LoRA adapters  | FP16 / BF16         |
| Router / gates | FP16                |
| Activations    | FP16                |
| Optimizer      | FP32                |

> `MXFP4`
>
> MXFP4 is much better for inference, especially for MoE:
>
> - Expert weights stay compressed
> - Routing stays fast
> - vLLM support is optimized

### Saving format

> Unsloth merging reconstructs full-precision MoE experts, applies LoRA safely
> per expert, stabilizes routing, and then re-encodes everything back into an
> inference-optimized MXFP4 form.

```
BNB-4bit experts + FP16 LoRA deltas
↓
Reconstruct FP16 experts
↓
Apply LoRA deltas per expert
↓
Stabilize routing layers
↓
Re-pack into MXFP4
↓
Save inference-ready model
```

## imatrix (Importance Matrix) quantize

Think of quantization like compressing a photo:

Basic quantization: Compresses everything equally (some important details get
blurry) imatrix quantization: Identifies which parts of the photo are _most
important_ (faces, text) and _preserves those while compressing backgrounds_
more aggressively

For neural networks:
Without imatrix: All weights quantized equally → some critical weights lose precision
With imatrix: Critical weights preserved at higher precision → better quality at same size

With full precision model(fp16 for gpt-oss), running test with datasets, llama
will record which parts of the parameters active, giving an importance score,
that one is imatrix. In quantized stage, imatrix will help to decide which parts
of the parameters deserve more accurate info.

**Importance analysis**:

- Query/Key weights: HIGH importance → 5-6 bits
- Bias terms: LOW importance → 3 bits
- Average: 4 bits
